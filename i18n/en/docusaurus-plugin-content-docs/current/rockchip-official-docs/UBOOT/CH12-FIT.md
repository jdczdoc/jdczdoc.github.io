# FIT

## Preface

This chapter will introduce the FIT format and the security/non-security boot scheme details based on the FIT format. For ease of introduction, this chapter mainly uses boot.img as the subject of explanation and operation throughout, but it is equally applicable to recovery.img.

## Introduction

### Basic Introduction

FIT (flattened image tree) is a new firmware type boot scheme supported by U-Boot, supporting arbitrary packaging and verification of multiple images. FIT uses an its (image source file) file to describe image information, and finally generates an itb (flattened image tree blob) image through the mkimage tool. The its file uses DTS syntax rules and is very flexible; you can directly use the libfdt library and related tools.

FIT is the default and recommended firmware format of U-Boot. Both the SPL and U-Boot stages support booting FIT format firmware. For more information, please refer to:

```
./doc/uImage.FIT/
```

Because the official FIT function cannot meet actual product requirements, the RK platform has adapted and optimized FIT. Therefore, in the FIT scheme, you must use the mkimage tool generated by RK U-Boot compilation, not the system's built-in mkimage.

### Example Introduction

The following uses u-boot.its and u-boot.itb as examples for introduction.

- `/images` : Statically defines all resources, equivalent to a dtsi file.
- `/configurations` : Each config node describes a set of bootable configurations, equivalent to a board-level dts file.
- `default =` : Specifies the default config to enable.

```c
/dts-v1/;

/ {
	description = "Simple image with OP-TEE support";
	#address-cells = <1>;

	images {
		uboot {
			description = "U-Boot";
			data = /incbin/("./u-boot-nodtb.bin");
			type = "standalone";
			os = "U-Boot";
			arch = "arm";
			compression = "none";
			load = <0x00400000>;
			hash {
				algo = "sha256";
			};
		};
		optee {
			description = "OP-TEE";
			data = /incbin/("./tee.bin");
			type = "firmware";
			arch = "arm";
			os = "op-tee";
			compression = "none";
			load = <0x8400000>;
			entry = <0x8400000>;
			hash {
				algo = "sha256";
			};
		};
		fdt {
			description = "U-Boot dtb";
			data = /incbin/("./u-boot.dtb");
			type = "flat_dt";
			compression = "none";
			hash {
				algo = "sha256";
			};
		};
	};

	// configurations can define any number of different conf nodes, but actual products only need one conf.
	configurations {
		default = "conf";
		conf {
			description = "Rockchip armv7 with OP-TEE";
			rollback-index = <0x0>;
			firmware = "optee";
			loadables = "uboot";
			fdt = "fdt";
			signature {
				algo = "sha256,rsa2048";
				padding = "pss";
				key-name-hint = "dev";
				sign-images = "fdt", "firmware", "loadables";
			};
		};
	};
};
```

### ITB Structure

itb is essentially a file set of fdt_blob + images. There are two packaging methods as follows. The RK platform scheme uses structure 2.

```C
	        fdt blob
|-----------------------------------|
|   |------|  |------|  |------|    |
|   | img0 |  | img1 |  | img2 |    |  Structure 1: images inside fdt_blob, i.e., itb = fdt_blob(including img)
|   |------|  |------|  |------|    |
|-----------------------------------|

|--------------|------|------|------|
|              |      |      |      |
|   fdt blob   | img0 | img1 | img2 |  Structure 2: images outside fdt_blob, i.e., itb = fdt_blob + img
|              |      |      |      |
|--------------|------|------|------|
```

### Image Files

The FIT scheme ultimately outputs two FIT format firmware for flashing: uboot.img (without trust.img) and boot.img, plus an SPL file for packaging into a loader.

- uboot.img File

  uboot.itb = trust + u-boot.bin + mcu.bin(option)

  uboot.img = uboot.itb * N copies (N is generally 2)

  > trust and mcu files come from the rkbin project; the compilation script automatically indexes and retrieves them from the rkbin project.

- boot.img File

  boot.itb = kernel + fdt + resource + ramdisk(optional)

  boot.img = boot.itb * M copies (M is generally 1)

- MCU Configuration

  Some platforms may include MCU firmware. Different products can decide whether to enable it based on the corresponding TRUST ini configuration. For example:

  ```c
  // File: RKTRUST/RV1126TOS_TB.ini, used for fast boot products, MCU enabled.
  [TOS]
  TOSTA=bin/rv11/rv1126_tee_ta_tb_v1.04.bin
  ADDR=0x00040000

  // MCU configuration format: firmware path, boot address, status (okay or disabled).
  // If disabled, the mcu will not be packaged into uboot.img.
  [MCU]
  MCU=bin/rv11/rv1126_mcu_v1.02.bin,0x108000,okay
  ```

- Firmware Compression

  Some platforms can support compression of sub-firmware inside uboot.img. Supported configurations:

  | Platform | Compression Format | Firmware                         |
  | -------- | ----------------- | -------------------------------- |
  | RV1126   | gzip, none        | u-boot.bin, trust, mcu(optional) |

  Users can add attributes in the corresponding TRUST ini file in the rkbin project to enable it. For example:

  ```c
  // File: RKTRUST/RV1126TOS_SPI_NOR_TINY.ini, used for small capacity SPI Nor products.
  [TOS]
  TOS=bin/rv11/rv1126_tee_v1.02.bin
  ADDR=0x08400000
  [MCU]
  MCU=bin/rv11/rv1126_mcu_v1.00.bin,0x208000,disabled

  // Compression format: gzip or none. If the following configuration field does not exist, it defaults to uncompressed.
  [COMPRESSION]
  COMPRESSION=gzip
  ```

- SPL File

  The SPL file refers to `spl/u-boot-spl.bin` generated after compilation completion, responsible for booting the FIT format uboot.img. Users need to use it to replace the closed-source miniloader on the RK platform, ultimately packaging the loader.

- `./fit` Directory

  After U-Boot compilation, the `./fit` folder is generated in the directory, containing some intermediate files, which will be introduced in subsequent sections.

boot.img and uboot.img are compiled and generated in the sdk project and uboot project respectively. However, boot.img supporting secure boot must be placed in the U-Boot project for repackaging and signing, as described in subsequent sections.

### ITS Files

- The its file for uboot is ./fit/u-boot.its, dynamically created by the script specified in defconfig via `CONFIG_SPL_FIT_GENERATOR`. Visible after successful firmware compilation.

- The its file for boot is located in the SDK project:

```c
device/rockchip/[platform]/xxx.its  // [platform] is the platform directory
```

The use of script tools will be introduced in subsequent sections. Here, we first focus on the parameters of make.sh:

**Optional parameters (users decide whether to pass based on actual situation):**

- `--spl-new`: Passing this parameter means using the spl file from the current compilation to package the loader; otherwise, use the spl file from the rkbin project.
- `--version-uboot [n]`: Specify the firmware version number of uboot.img. n must be a positive decimal integer.
- `--version-boot [n]`: Specify the firmware version number of boot.img. n must be a positive decimal integer.
- `--version-recovery [n]`: Specify the firmware version number of recovery.img. n must be a positive decimal integer.

**Required parameters (when enabling secure boot):**

- `--rollback-index-uboot [n]`: Specify the anti-rollback version number of uboot.img firmware. n must be a positive decimal integer.
- `--rollback-index-boot [n]`: Specify the anti-rollback version number of boot.img firmware. n must be a positive decimal integer.
- `--rollback-index-recovery [n]`: Specify the anti-rollback version number of recovery.img firmware. n must be a positive decimal integer.
- `--no-check`: Used when packaging secure firmware, to skip the self-verification of the secure firmware packaging script.

> Description:
>
> 1. Firmware anti-rollback version number: Only allowed to be activated when secure boot is enabled. This version number is saved in OTP or other secure storage. Main purpose: To prevent firmware version rollback for vulnerability attacks.
>
> 2. Firmware version number: Optional. Defaults to 0 if not specified. Main purpose: Serves as a firmware version identifier, convenient for users to perform version management of firmware.

## Secure Boot

The FIT scheme supports secure boot with the following related features:

- sha256 + rsa2048 + pkcs-v2.1(pss) padding
- Firmware anti-rollback
- Firmware re-signing (remote signing)
- Crypto hardware acceleration

### Principle

#### Verification Flow

- Maskrom verifies loader (including SPL, ddr, usbplug)
- SPL verifies uboot.img (including trust, U-Boot...)
- U-Boot verifies boot.img (including kernel, fdt, ramdisk...)

Currently, only sha256+rsa2048+pkcs-v2.1(pss) padding secure verification mode is supported by default.

#### Key Usage

From Maskrom to kernel, a single RSA public key is used for security verification:

- Maskrom verifies loader.

  The RSA public key needs to be written into the loader file header using the PC tool `rk_sign_tool`. During secure boot, Maskrom first obtains the RSA public key from the loader firmware header and verifies its validity; then uses this public key to verify the loader's firmware signature.

  > rk_sign_tool can be obtained from the rkbin repository. U-Boot will automatically complete the loader signing.

- SPL verifies U-Boot and trust.

  SPL stores the RSA public key in u-boot-spl.dtb, which is packaged into u-boot-spl.bin (ultimately packaged into the loader). During secure boot, SPL reads the RSA public key from its dtb file to perform security verification on uboot.img.

- U-Boot verifies boot.

  U-Boot stores the RSA public key in u-boot.dtb, which is packaged into u-boot.bin (ultimately packaged as uboot.img). During secure boot, U-Boot reads the RSA public key from its dtb file to verify boot.img.

Therefore, the RSA Key at the current level is already part of its own firmware, and its security is ensured by the previous loader's security verification.

#### Signature Storage

The RSA signature result is stored in the itb file. The signed content is specified by `hashed-nodes`: including the entire `conf` node attributes, packaged firmware nodes, etc.

Below is the signature information of u-boot.itb, similarly for boot.itb:

#### Anti-Rollback

- Secure boot supports specifying the current firmware version number for boot.img and uboot.img respectively. If the current firmware version number is less than the minimum version number on the machine, boot is not allowed.

- Minimum version number update: After completing security verification and confirming the system can boot normally, it is updated to OTP or secure storage.

### Preliminary Preparation

#### Key

Executing the following three commands in the U-Boot project can generate an RSA key pair for signing. Usually, it only needs to be generated once. After that, this key pair is used to sign and verify firmware. Please keep it safe.

```c
// 1. Key directory: keys
mkdir -p keys

// 2. Use RK's "rk_sign_tool" tool to generate RSA2048 private key privateKey.pem and public key publicKey.pem, rename and store them as: keys/dev.key and keys/dev.pubkey. Command:
../rkbin/tools/rk_sign_tool kk --bits 2048 --out .

// 3. Use -x509 and private key to generate a self-signed certificate: keys/dev.crt (functionally equivalent to public key)
openssl req -batch -new -x509 -key keys/dev.key -out keys/dev.crt
```

> If there is an error about missing .rnd file in the user directory:
>
> Can't load /home4/cjh//.rnd into RNG
> ...
> Please create it manually first: touch ~/.rnd

`ls keys/` to view results:

```
dev.crt  dev.key  dev.pubkey
```

> Note: The names "keys", "dev.key", "dev.crt", and "dev.pubkey" must not be changed. These names are already statically defined in the its file; changing them will cause packaging failure.

## Remote Signing

From the above sections, creating secure firmware requires users to do it on their local PC, meaning users must possess: RSA key pair and firmware. However, in practice, users may need to upload firmware to a remote server, where the server holds the RSA private key to complete the signing, and then return the signed firmware to the local user. For this situation, the RK FIT scheme implements it through "re-signing".

### Implementation Approach

- Since users can only obtain the server's public key, they first use a temporary private key + server's public key to perform one packaging sign on the local PC, generating a secure firmware with a temporary signature and signed data.

  > The public key is used to package the public key into the dtb file for use during the secure boot flow; the private key is used for temporary signing.

- Users send the signed data to the server (not the entire firmware, saving time), and the server uses the private key to sign the signed data and returns the signature to the user.

- Users replace the temporary signature in the secure firmware with this signature to obtain the final secure firmware for burning.

### Signed Data

The signed data mentioned in the above section includes: fdt blob configuration + sub-image hash collection.

- fdt blob node configuration

  `hashed-nodes` specifies a series of nodes, and the contents of these nodes are included in the signed data.

  ```c
  cjh@ubuntu:~/uboot-nextdev$ fdtdump uboot.img | less
  /dts-v1/;
  ......

  configurations {
          default = "conf";
          conf {
              description = "Rockchip armv7 with OP-TEE";
              rollback-index = <0x0000001c>;
              firmware = "optee";
              loadables = "uboot";
              fdt = "fdt";

              signature {
                  hashed-strings = <0x00000000 0x000000da>;
                  // These node contents will be included in the signed data
                  hashed-nodes = "/", "/configurations/conf", "/images/fdt", "/images/fdt/hash", "/images/optee", "/images/optee/hash", "/images/uboot", "/images/uboot/hash";
                  ......
  ```

- Sub-image hash collection.

  mkimage automatically generates hash values for each sub-image and appends them to the hash node. All sub-image hash values specified by `sign-images` are included in the signed data (essentially specified through `hashed-nodes` specifying hash nodes). For example:

  ```c
  cjh@ubuntu:~/uboot-nextdev/u-boot$ fdtdump fit/u-boot.itb | less

  /dts-v1/;
  ......

  / {
      totalsize = <0x000bb600>;
      timestamp = <0x5ecb3553>;
      description = "Simple image with OP-TEE support";
      #address-cells = <0x00000001>;
      images {
          uboot {
              data-size = <0x0007ed54>;
              data-position = <0x00000a00>;
              description = "U-Boot";
              type = "standalone";
              os = "U-Boot";
              arch = "arm";
              compression = "none";
              load = <0x00400000>;
              hash {
                  // uboot image hash, automatically calculated by mkimage
                  value = <0xeda8cd52 0x8f058118 0x00000003 0x35360000 0x6f707465 0x0000009f 0x00000091 0x00000000>;
                  algo = "sha256";
              };
          };
          ......
  ```

### Specific Steps

The RSA key pair for signing firmware is: dev.key, dev.pubkey, and dev.crt. dev.key is held by the remote server as the private key, while users only have dev.pubkey and dev.crt.

**Step 1:**

In the local U-Boot project environment: users put dev.crt in the keys directory, then use RK's "rk_sign_tool" tool to randomly generate a temporary private key, name it dev.key, and put it in the keys directory. Refer to the above section (but add `--no-check` to the compilation parameters) to generate signed firmware uboot.img and boot.img (these will not be used in the end; users need the intermediate files).

Note: **The compile command must include the parameter `--no-check`**, otherwise the packaging script will fail self-verification because dev.key and dev.crt do not match. For example:

```c
./make.sh rv1126 --spl-new --boot_img boot.img --rollback-index-uboot 10 --rollback-index-boot 12 --no-check
```

Besides generating signed firmware uboot.img and boot.img, users can also get intermediate files in the `fit/` directory:

```c
// Signed content (data2sign means data to sign)
fit/uboot.data2sign
fit/boot.data2sign

// Signed itb file (using temporary private key), from which our img file is obtained after multiple backups.
fit/uboot.itb
fit/boot.itb
```

**Step 2:**

Users send uboot.data2sign to the remote server. Assuming the server holds the private key dev.key, use the following command to sign and output the signature result: uboot.sig

```
openssl dgst -sha256 -sign dev.key -sigopt rsa_padding_mode:pss -out uboot.sig uboot.data2sign
```

The server returns the signature result file uboot.sig to the user, who then uses uboot.sig to replace the temporary signature in uboot.itb:

```c
./scripts/fit-resign.sh -f fit/uboot.itb -s uboot.sig // Will generate a new uboot.img for flashing
```

Similarly for the boot.itb file. Thus the user obtains the final valid signed firmware uboot.img and boot.img.

**Precautions:**

- The -f parameter of fit-resign.sh specifies the itb file, not the img file. The script re-signs the itb and generates an img file.
- The itb file used when executing fit-resign.sh must be the one generated in step 1, because the itb file and data2sign file have a one-to-one correspondence. The data2sign information contains the timestamp of generating the itb file, i.e., `/timestamp = <...>`. Therefore, even if there is no code change, recompiling to obtain a new uboot.itb and replacing uboot.sig into the new uboot.itb will cause secure boot failure!
- Since there is no private key, the loader needs to be sent to the server separately for signing.

### Other Schemes

Besides the "re-signing" method, is it possible to directly upload the entire firmware (boot.img, uboot.img) or discrete images (u-boot.bin, fdt, ramdisk, kernel ...) to the server for signing?

Based on the design principles and implementation of FIT, implementing other schemes is relatively difficult. The following explains:

- Scheme 1: Upload non-secure boot.img and uboot.img to the server for repackaging + signing.

  Problem: Also need to upload configuration information from the local U-Boot compilation environment, u-boot-spl.bin file, etc.

- Scheme 2: Upload secure boot.img and uboot.img to the server for repackaging + signing.

  Problem: The local compilation of firmware has already packaged the RSA public key; the server would package the RSA public key a second time.

- Scheme 3: Upload all discrete images (kernel, dtb, ramdisk, resource...) for packaging + signing.

  Problem: Too many files to upload, which is cumbersome, and also has the same issues as Scheme 1.

> Common problem with all the above schemes: The server must use the RK mkimage tool, which may be updated by RK.

Therefore, the current "re-signing" method is the simplest to operate, has no dependencies, and is the least error-prone: users only need to upload the signed data, and the server only needs to use the openssl command to sign.

## Security Verification Step-by-Step

1. Enter the u-boot directory, open the corresponding platform's configs/rxxxxx_defconfig, and select the following configurations:

```c
// Required.
CONFIG_FIT_SIGNATURE=y
CONFIG_SPL_FIT_SIGNATURE=y

// Optional.
CONFIG_FIT_ROLLBACK_PROTECT=y       // boot.img anti-rollback
CONFIG_SPL_FIT_ROLLBACK_PROTECT=y   // uboot.img anti-rollback
```

2. Execute the following to generate keys:

```shell
mkdir -p keys
../rkbin/tools/rk_sign_tool kk --bits 2048 --out .
cp privateKey.pem keys/dev.key && cp publicKey.pem keys/dev.pubkey
openssl req -batch -new -x509 -key keys/dev.key -out keys/dev.crt
```

**Note: Execute this step only once, then keep these keys safe.**

3. Compile and sign, using rv1126 as an example (to compile and sign firmware for other chips like rk3566, replace rv1126 with rk3566 in the following commands):

```shell
// Linux: Copy boot.img, recovery.img to the u-boot directory, execute the following script to sign loader, uboot, boot, recovery, set the anti-rollback version numbers for uboot, boot, recovery. Note that the anti-rollback version numbers are configured as needed.
./make.sh rv1126 --spl-new --boot_img boot.img --recovery_img recovery.img --rollback-index-uboot 1 --rollback-index-boot 2

// Android: Sign loader and uboot, set the anti-rollback version number for uboot. Note that the anti-rollback version number is configured as needed.
./make.sh rv1126 --spl-new --rollback-index-uboot 1
```

If compilation shows:

```
Can't load XXXXXX//.rnd into RNG
```

Execute:

```shell
touch ~/.rnd
```

4. Public key hash burning:

```shell
// Linux: Copy boot.img, recovery.img to the u-boot directory, execute the following script to sign loader, uboot, boot, recovery, set anti-rollback version numbers for uboot, boot, recovery, enable key hash burning.
./make.sh rv1126 --spl-new --boot_img boot.img --recovery_img recovery.img --rollback-index-uboot 1 --rollback-index-boot 2 --burn-key-hash

// Android: Sign loader, uboot, set the anti-rollback version number for uboot, enable key hash burning.
./make.sh rv1126 --spl-new --rollback-index-uboot 1 --burn-key-hash
```

**Note: Configure `--burn-key-hash` only after the entire product development and verification is complete; otherwise, once security is enabled, only signed firmware can be updated during product development.**
