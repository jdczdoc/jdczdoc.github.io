# Driver Modules

## Interrupt

### Framework Support

U-Boot's native code does not have an interrupt framework. RK implemented its own set to support GICv2/v3, enabled by default.

Currently, interrupt scenarios include:

- Pwrkey: When U-Boot is charging, the CPU enters low-power sleep and needs to be woken up via Pwrkey interrupt;
- Timer: Timer interrupts are used in U-Boot charging and test cases;
- Debug: Enable the CONFIG_ROCKCHIP_DEBUGGER debugging feature;

Configuration:

```
CONFIG_IRQ
CONFIG_GICV2
CONFIG_GICV3
```

Framework code:

```
./drivers/irq/irq-gpio-switch.c
./drivers/irq/irq-gpio.c
./drivers/irq/irq-generic.c
./drivers/irq/irq-gic.c
./drivers/irq/virq.c
./include/irq-generic.h
```

### Related Interfaces

```c
// CPU local interrupt control
void enable_interrupts(void);
int disable_interrupts(void);

// GPIO to interrupt number conversion
int gpio_to_irq(struct gpio_desc *gpio);
int phandle_gpio_to_irq(u32 gpio_phandle, u32 pin);
int hard_gpio_to_irq(unsigned gpio);

// Register/release interrupt callbacks
void irq_install_handler(int irq, interrupt_handler_t *handler, void *data);
void irq_free_handler(int irq);

// Enable/disable interrupt
int irq_handler_enable(int irq);
int irq_handler_disable(int irq);

// Interrupt trigger type
int irq_set_irq_type(int irq, unsigned int type);
```

**Requesting IRQ**

- Peripherals with dedicated hardware interrupt numbers do not require additional conversion, e.g., pwm, timer, etc.
- GPIO pins do not have dedicated hardware interrupt numbers and require additional conversion.

There are 3 ways to request a GPIO pin interrupt number:

(1) Passing `struct gpio_desc`

```c
// This method can dynamically parse dts configuration, making it flexible and commonly used.
int gpio_to_irq(struct gpio_desc *gpio);
```

Example:

```c
battery {
	compatible = "battery,rk817";
	......
	dc_det_gpio = <&gpio2 7 GPIO_ACTIVE_LOW>;
	......
};
```

```c
struct gpio_desc dc_det;
int ret, irq;

ret = gpio_request_by_name_nodev(dev_ofnode(dev), "dc_det_gpio", 0,
                                 &dc_det, GPIOD_IS_IN);
// Return value check omitted for simplicity
if (!ret) {
	irq = gpio_to_irq(&dc_det);
	irq_install_handler(irq, ...);
	irq_set_irq_type(irq, IRQ_TYPE_EDGE_FALLING);
	irq_handler_enable(irq);
}
```

(2) Passing the gpio phandle and pin

```c
// This method can dynamically parse dts configuration, making it flexible and commonly used.
int phandle_gpio_to_irq(u32 gpio_phandle, u32 pin);
```

Example (rk817 interrupt pin is GPIO0_A7):

```c
rk817: pmic@20 {
	compatible = "rockchip,rk817";
	reg = <0x20>;
	......
	interrupt-parent = <&gpio0>;             // "&gpio0": points to the phandle of the gpio0 node;
	interrupts = <7 IRQ_TYPE_LEVEL_LOW>;     // "7": pin number;
	......
};
```

```c
u32 interrupt[2], phandle;
int irq, ret;

phandle = dev_read_u32_default(dev->parent, "interrupt-parent", -1);
if (phandle < 0) {
	printf("failed get 'interrupt-parent', ret=%d\n", phandle);
	return phandle;
}

ret = dev_read_u32_array(dev->parent, "interrupts", interrupt, 2);
if (ret) {
	printf("failed get 'interrupt', ret=%d\n", ret);
	return ret;
}

// Return value check omitted for simplicity
irq = phandle_gpio_to_irq(phandle, interrupt[0]);
irq_install_handler(irq, pwrkey_irq_handler, dev);
irq_set_irq_type(irq, IRQ_TYPE_EDGE_FALLING);
irq_handler_enable(irq);
```

(3) Forcing a specific gpio

```c
// This method directly forces a specific gpio. The passed gpio must be declared using special macros, which is not flexible and is not recommended.
int hard_gpio_to_irq(unsigned gpio);
```

Example (GPIO0_A0 requesting interrupt):

```c
int gpio0_a0, irq;

// Return value check omitted for simplicity
gpio0_a0 = RK_IRQ_GPIO(RK_GPIO0, RK_PA0);
irq = hard_gpio_to_irq(gpio0_a0);
irq_install_handler(irq, ...);
irq_handler_enable(irq);
```

### Clock Initialization

There are three types of interfaces related to clock initialization. The cru node information is listed below for reference in the subsequent introduction.

```
cru: clock-controller@ff2b0000 {
	compatible = "rockchip,px30-cru";
	......
	assigned-clocks =
		<&pmucru PLL_GPLL>, <&pmucru PCLK_PMU_PRE>,
		<&pmucru SCLK_WIFI_PMU>, <&cru ARMCLK>,
		<&cru ACLK_BUS_PRE>, <&cru ACLK_PERI_PRE>,
		<&cru HCLK_BUS_PRE>, <&cru HCLK_PERI_PRE>,
		<&cru PCLK_BUS_PRE>, <&cru SCLK_GPU>;
	assigned-clock-rates =
		<1200000000>, <100000000>,
		<26000000>, <600000000>,
		<200000000>, <200000000>,
		<150000000>, <150000000>,
		<100000000>, <200000000>;
	......
}
```

**Type 1, Platform base clock default initialization: `rkclk_init()`**

Each platform's cru driver probe calls `rkclk_init()` to complete pll/cpu/bus frequency initialization, with frequencies defined in `cru_rkxxx.h`. For example RK3399:

```c
#define APLL_HZ         (600 * MHz)
#define GPLL_HZ         (800 * MHz)
#define CPLL_HZ         (384 * MHz)
#define NPLL_HZ         (600 * MHz)
#define PPLL_HZ         (676 * MHz)
#define PMU_PCLK_HZ     ( 48 * MHz)
#define ACLKM_CORE_HZ   (300 * MHz)
#define ATCLK_CORE_HZ   (300 * MHz)
#define PCLK_DBG_HZ     (100 * MHz)
#define PERIHP_ACLK_HZ  (150 * MHz)
#define PERIHP_HCLK_HZ  ( 75 * MHz)
#define PERIHP_PCLK_HZ  (37500 * KHz)
#define PERILP0_ACLK_HZ (300 * MHz)
#define PERILP0_HCLK_HZ (100 * MHz)
#define PERILP0_PCLK_HZ ( 50 * MHz)
#define PERILP1_HCLK_HZ (100 * MHz)
#define PERILP1_PCLK_HZ ( 50 * MHz)
......
```

**Type 2, Platform base clock secondary initialization: `clk_set_defaults()`**

Each platform's cru driver probe may call `clk_set_defaults()` to parse and configure the frequencies specified by `assigned-clocks/assigned-clock-parents/assigned-clock-rates` within the cru node (i.e., reconfigure the frequencies), excluding the ARM frequency. It is only configured when `set_armclk_rate()` is implemented.

In addition to cru, peripherals with such requirements can also actively call `clk_set_defaults()` in their own probe, e.g., vop, gmac.

**Type 3, Individual module clock initialization: `clk_set_rate()`**

Most peripheral modules use `clk_set_rate()` to configure their own frequencies.

### CPU Frequency Scaling

The implementation flow for CPU frequency scaling at boot:

- Step 1: Specify the ARM target frequency in the `assigned-clocks` of the cru node;
- Step 2: The cru driver probe calls `clk_set_defaults()` to obtain (but not configure) the ARM target frequency from Step 1;
- Step 3: Implement `set_armclk_rate()`, which is a __weak function that configures the ARM target frequency obtained from Step 2;
- Step 4: Add `regulator-init-microvolt = <...>` in the ARM regulator node to specify the init voltage to avoid insufficient voltage;

### Clock Tree

The U-Boot framework does not provide clock tree management. Each platform adds `soc_clk_dump()` for simple clock information printing. For example:

````
CLK: (sync kernel. arm: enter 1200000 KHz, init 1200000 KHz, kernel 800000 KHz)
  apll 800000 KHz
  dpll 392000 KHz
  cpll 1000000 KHz
  gpll 1188000 KHz
  npll 24000 KHz
  ppll 100000 KHz
  hsclk_bus 297000 KHz
  msclk_bus 198000 KHz
  lsclk_bus 99000 KHz
  msclk_peri 198000 KHz
  lsclk_peri 99000 KHz
````

Meaning of the first line:

- `sync kernel`: The cru driver configures the bus frequencies specified in the kernel cru node via `clk_set_defaults()` (excluding ARM frequency); otherwise, it displays sync uboot;
- `enter 1200000 KHz`: The ARM frequency when the previous stage Loader enters U-Boot;
- `init 1200000 KHz`: The ARM init frequency in U-Boot, i.e., the frequency defined by APLL_HZ;
- `kernel 800000 KHz`: `set_armclk_rate()` is implemented and sets the ARM frequency specified in `assigned-clocks` of the kernel cru node; otherwise, it displays "kernel 0N/A";

### Related Interfaces

```c
// Request/release GPIO
int gpio_request_by_name(struct udevice *dev, const char *list_name,
                         int index, struct gpio_desc *desc, int flags);
int gpio_request_by_name_nodev(ofnode node, const char *list_name, int index,
                               struct gpio_desc *desc, int flags);
int gpio_request_list_by_name(struct udevice *dev, const char *list_name,
                              struct gpio_desc *desc_list, int max_count, int flags);
int gpio_request_list_by_name_nodev(ofnode node, const char *list_name,
                                    struct gpio_desc *desc_list, int max_count,
                                    int flags);

// Configure GPIO direction. @flags: GPIOD_IS_OUT (output) and GPIOD_IS_IN (input)
int dm_gpio_set_dir_flags(struct gpio_desc *desc, ulong flags);

// Get/set GPIO level
int dm_gpio_get_value(const struct gpio_desc *desc)
int dm_gpio_set_value(const struct gpio_desc *desc, int value)
```

**Notes:**

The return value of `dm_gpio_get_value()` represents the active state, not the electrical high or low level. For example:

- `gpios = <&gpio2 RK_PD0 GPIO_ACTIVE_LOW>`, returns 1 when low, 0 when high.

- `gpios = <&gpio2 RK_PD0 GPIO_ACTIVE_HIGH>`, returns 0 when low, 1 when high.

The value parameter of `dm_gpio_set_value()` follows the same logic: 1 = active, 0 = inactive.

## Display

### Framework Support

RK U-Boot currently supports the following display interfaces: RGB, LVDS, EDP, MIPI and HDMI. CVBS, DP, etc. will be added in the future. The U-Boot display logo images come from logo.bmp and logo_kernel.bmp in the kernel root directory, which are packaged into resource.img.

Image requirements:

- 8bit or 24bit BMP format;

- logo.bmp and logo_kernel.bmp must have the same resolution;

- For chips based on the vop lite architecture such as rk312x/px30/rk3308, since VOP does not support mirroring and 24bit BMP images are stored mirrored, if the displayed image appears mirrored in the y-direction, please mirror the image in the y-direction on the PC side beforehand.

### LOGO Partition

If users need to dynamically update the boot LOGO (typically initiated at the application layer), this can be achieved through an independent LOGO partition.

Operation steps:

- Add an independent LOGO partition in the partition table.

- Dynamically update the image in the LOGO partition as needed. When updating, users can directly write the raw image to the LOGO partition without any packaging. If the image in the LOGO partition is invalid, the default image from the resource file will be used instead.

**LOGO partition support:**

If the code only includes the following commit, the LOGO partition supports only 1 image, which can only replace the default logo.bmp:

  ```
  1d30bcc rockchip: resource: support parse "logo" partition picture
  ```

If the code includes the following commit, the LOGO partition supports 2 images: image 1 replaces logo.bmp, image 2 replaces logo_kernel.bmp. The two images are adjacent, with 512-byte alignment between them, and the order must not be swapped.

  ```
  commit 07f987d8d495380787203e2bc2accd44100e6051
  Author: Joseph Chen <chenjh@rock-chips.com>
  Date:   Sun Dec 8 18:00:37 2019 +0800

      rockchip: resource: support parse logo_kernel.bmp from logo partition

      "logo" partition layout, not change order:

      |----------------------| 0x00
      | raw logo.bmp         |
      |----------------------| N*512-byte aligned
      | raw logo_kernel.bmp  |
      |----------------------|

      N: the sector count of logo.bmp

      Signed-off-by: Joseph Chen <chenjh@rock-chips.com>
      Change-Id: I2deba013d3963c99664c5bfd69693835a46ba48f
  ```

Assuming the images are logo.bmp and logo_kernel.bmp respectively. logo.img packaging command:

```shell
cat logo.bmp > logo.img && truncate -s %512 logo.img && cat logo_kernel.bmp >> logo.img
```

### Init Voltage

There are currently two ways to set the initial voltage output for a regulator, provided that `regulator-boot-on` is configured:

- Set `regulator-min-microvolt` and `regulator-max-microvolt` to the same value;

- Configure `regulator-init-microvolt = <...>`

```c
vdd_arm: DCDC_REG1 {
	regulator-name = "vdd_arm";
	regulator-boot-on;                      // Must be configured
	regulator-min-microvolt = <712500>;
	regulator-max-microvolt = <1450000>;
	regulator-init-microvolt = <1100000>;   // Set initial voltage to 1.1v
	......
};
```

### Skipping Initialization

To skip initialization of a particular regulator, add `regulator-loader-ignore`.

```c
vdd_arm: DCDC_REG1 {
	regulator-name = "vdd_arm";
	regulator-loader-ignore;// Only effective for regulator initialization in U-Boot stage, not kernel
	......
};
```

## Vendor Storage

Vendor Storage is used to store small data that does not require encryption, such as SN, MAC, etc. The data is stored in reserved partitions of NVM (eMMC, NAND, etc.), with multiple backups. Data is not lost when updating, ensuring high reliability.

For detailed information, refer to the document "appnote rk vendor storage".

### Principle Overview

The vendor storage block is divided into 4 partitions: vendor0, vendor1, vendor2, vendor3. The hdr of each vendorX (X=0, 1, 2, 3) contains a monotonically increasing version field indicating when vendorX was last updated. Each read operation only reads the latest vendorX (i.e., with the highest version). During a write operation, the version is updated and the entire existing information along with the new information is moved to the vendorX+1 partition. For example, if information is currently read from vendor2, after modification and writing back, it is written to vendor3. This is done for simple security protection.

## DVFS

The DVFS in this chapter differs from the kernel. It is a dynamic frequency and voltage scaling mechanism specifically designed for wide-temperature chips.

### Wide-Temperature Strategy

The U-Boot framework does not support DVFS. To support the wide-temperature function of certain chips, RK implemented a DVFS wide-temperature driver that adjusts the cpu/dmc frequency and voltage based on the chip temperature. However, unlike the kernel DVFS driver, this wide-temperature driver only performs control when the high/low temperature thresholds are triggered.

**Wide-temperature strategy:**

1. The wide-temperature driver is used to adjust the cpu/dmc frequency and voltage. The control strategy can take effect for both cpu and dmc simultaneously, or only one of them, as determined by dts configuration; the cpu and dmc control strategies are the same;
2. The wide-temperature driver parses the opp table, regulator, clock, and thermal zone's "trip-point-0" of the cpu/dmc node to obtain frequency-voltage levels, high/low temperature thresholds, maximum allowed voltage, etc.;
3. If the cpu/dmc opp table specifies `rockchip,low-temp = <...>` or `rockchip,high-temp = <...>`, or the cpu/dmc references the trip node of the thermal zone, then the cpu/dmc wide-temperature control strategy will take effect;
4. Key attributes:

- rockchip,low-temp: Minimum temperature threshold, denoted as TEMP_min below;
- rockchip,high-temp and thermal zone: Maximum temperature threshold, denoted as TEMP_max below (if both are valid, the current temperature will be compared against both in the strategy);
- rockchip,max-volt: Maximum allowed voltage value, denoted as V_max below;

5. Threshold trigger handling:

- If the temperature is above TEMP_max, reduce both frequency and voltage to the lowest level;
- If the temperature is below TEMP_min, increase voltage by 50mv by default. If a 50mv increase would cause the voltage to exceed V_max, set the voltage to V_max and reduce the frequency by 2 levels;

6. Currently, the wide-temperature strategy is applied at 2 time points:

- After the regulator and clk framework initialization is complete, the wide-temperature driver initializes and executes the wide-temperature strategy once. This is called in board_init() in the board.c file;
- During the preboot phase (i.e., before loading firmware), the wide-temperature strategy is executed again: if the dts node specifies "repeat" or related properties (see below), and after executing this wide-temperature strategy the chip temperature is still not within the temperature threshold range, system startup will be halted and the wide-temperature strategy will be continuously executed until the chip temperature returns to the threshold range before continuing system startup. If there are no "repeat" or related properties, the system starts directly after executing this wide-temperature strategy. Currently, the repeat attribute is generally not needed.

### Enabling the Feature

1. Making amp.img requires an its file. Please modify based on `drivers/cpu/amp.its`:

   ```c
   /dts-v1/;
   / {
   	description = "FIT source file for rockchip AMP";
   	#address-cells = <1>;

   	images {
   		amp0 {
   			description  = "bare-mental-core0";           // Required: description
   			data         = /incbin/("../../hal0.bin");    // Required: amp0 firmware
   			type         = "firmware";
   			compression  = "none";
   			arch         = "arm";      // Required: "arm64": 64-bit, "arm": 32-bit
   			cpu          = <0x000>;    // Required: cpu hardware id (mpidr)
   			thumb        = <0>;        // Required: 0: arm or thumb2; 1: pure thumb
   			hyp          = <0>;        // Required: 0: el1/svc; 1: el2/hyp
   			load         = <0xa00000>; // Required: firmware load and run address
   			udelay       = <500000>;   // Optional: delay after starting current CPU before starting the next CPU
   			linux-os;                  // Special optional!
   			hash {
   				algo = "sha256";
   			};
   		};

   		amp1 {
   			......
   		};

   		amp2 {
   			......
   		};

   		amp3 {
   			......
   		};
   	};

   	configurations {
   		default = "conf";
   		conf {
   			description = "Rockchip AMP images";
   			rollback-index = <0x0>;
   			// Specify the firmware to be loaded and the order.
   			loadables = "amp0", "amp1", "amp2", "amp3";
   			signature {
   				algo = "sha256,rsa2048";
   				padding = "pss";
   				key-name-hint = "dev";
   				sign-images = "loadables";
   			};
   		};
   	};
   };
   ```

Explanation:

- Main CPU: The CPU that is currently running U-Boot and is responsible for starting other cores is called the "main CPU". The main CPU's state is the last to be switched.

- data: Firmware path. This path is relative to amp.its.

- arch: CPU 32/64-bit mode. ARMv7 can only be "arm"; ARMv8 can specify "arm64" or "arm" for AArch64 or AArch32 respectively.

- cpu: CPU hardware ID, i.e., mpidr (Multiprocessor Affinity Register), take the (lower) 32 bits. For example:

  ```c
  cpus {
  	#address-cells = <2>;
  	#size-cells = <0>;

  	cpu0: cpu@0 {
  		device_type = "cpu";
  		compatible = "arm,cortex-a55";
  		reg = <0x0 0x0>;	// mpidr
  		......
  	};

  	cpu1: cpu@100 {
  		device_type = "cpu";
  		compatible = "arm,cortex-a55";
  		reg = <0x0 0x100>;	// mpidr
  		......
  	};
  	......
  };
  ```

- thumb: CPU instruction mode. Set to 1 for pure thumb, otherwise 0.

- hyp: CPU virtualization mode.

- load: Firmware load and run address.

- udelay: Delay after loading, in us. After starting the current CPU, do the corresponding delay before starting the next CPU.

- loadables: AMP firmware load order. The main CPU is loaded last and is not affected by the order specified here.

- linux-os: The main CPU runs Linux. Optional, can only be added under the main CPU's node. If this attribute exists:

  - After the main CPU starts the other cores, it continues to run Linux (i.e., following the original flow and firmware format, loaded and started by U-Boot).

  - The main CPU node must still be specified in "loadables".

  - The "data" and "load" fields in the main CPU node have no practical effect but must still be retained, otherwise mkimage packaging will report an error.

    > It is recommended to create an empty file for the data field, e.g., touch hal0.bin.

- Special note: AMP OS must handle memory management individually to avoid memory conflicts.

2. Firmware packaging:

   ```c
   // 0xe00 is the firmware header size, not recommended to change
   ./tools/mkimage -f ./drivers/cpu/amp.its -E -p 0xe00 amp.img
   ```

   > A full U-Boot compilation is required to automatically generate the mkimage tool.

3. Add amp partition to the partition table

   Add the "amp" partition to the parameter.txt partition table file, then flash amp.img.

   > U-Boot directly loads the entire content of the amp partition into memory. It is recommended to configure the amp partition size according to actual needs.

### DTS Configuration

The DTS node is the same as the kernel. The following board-level attribute configurations need attention:

- phy interface configuration (phy-mode)

- phy reset pin and reset time (snps,reset-gpio) (snps,reset-delays-us)

- Clock output direction for the controller (clock_in_out)

- Clock source selection and frequency setting (assigned-clock-parents) (assigned-clock-rates)

- RGMII Delayline, required for RGMII interface (tx_delay) (rx_delay)

```c
&gmac {
	phy-mode = "rgmii";
	clock_in_out = "input";

	snps,reset-gpio = <&gpio3 RK_PA0 GPIO_ACTIVE_LOW>;
	snps,reset-active-low;
	/* Reset time is 20ms, 100ms for rtl8211f */
	snps,reset-delays-us = <0 20000 100000>;

	assigned-clocks = <&cru CLK_GMAC_SRC>, <&cru CLK_GMAC_TX_RX>, <&cru CLK_GMAC_ETHERNET_OUT>;
	assigned-clock-parents = <&cru CLK_GMAC_SRC_M1>, <&cru RGMII_MODE_CLK>;
	assigned-clock-rates = <125000000>, <0>, <25000000>;

	pinctrl-names = "default";
	pinctrl-0 = <&rgmiim1_pins &clk_out_ethernetm1_pins>;

	tx_delay = <0x2a>;
	rx_delay = <0x1a>;

	phy-handle = <&phy>;
	status = "okay";
};
```

### Network Troubleshooting

**1. Network environment, common aspects:**

- Is the firewall on the PC turned off;

- If crossing network segments, confirm whether the gateway is set;

- Is the TFTP server configured correctly;

- Is the TFTP function of some routers disabled.

**2. Code issues, generally confirm the following 3 areas:**

- Is the pinctrl configuration correct. Check if the iomux and drive strength of the relevant pins are correct. You can also dump the relevant registers and compare with the kernel to see if they match. In most cases, we debug the kernel network first before debugging U-Boot.

- Is the clock configuration correct. Clock configuration checking is relatively more complex. Mainly check the division ratio, clock source, and clock direction. Most registers are in CRU, but some chips have some registers in GRF. You can also dump the relevant registers and compare with the kernel to see if they match.

- PHY reset pin. Mainly check whether the reset pin configuration is correct and whether the reset waveform meets the PHY requirements.
