# Advanced Principles

## kernel-DTB

### Design Background

The native architecture of U-Boot requires that one board must correspond to one U-Boot dts, and the dtb generated from the U-Boot dts is packaged into U-Boot's own image. This results in N boards requiring N U-Boot images on each SoC platform.

It is not difficult to see that the main differences between different boards on the same SoC platform are peripherals, while the SoC core part is identical. To achieve the goal that one SoC platform requires only one U-Boot image, the RK platform added the kernel DTB mechanism. The essence is to switch to the kernel DTB at an early stage and use its configuration information to initialize peripherals.

Therefore, by supporting kernel DTB, the RK platform can achieve compatibility with board differences, such as: display, pmic/regulator, pinctrl, clk, etc.

Enabling kernel DTB depends on OF_LIVE (live device tree, referred to as: live-dt).

```
config USING_KERNEL_DTB
        bool "Using dtb from Kernel/resource for U-Boot"
        depends on RKIMG_BOOTLOADER && OF_LIVE
        default y
        help
          This enable support to read dtb from resource and use it for U-Boot,
          the uart and emmc will still using U-Boot dtb, but other devices like
          regulator/pmic, display, usb will use dts node from kernel.
```

### Live device tree

**Background and Principle:**

After introducing kernel DTB, there are two DTBs in the U-Boot phase. Modules such as storage, serial port, and Crypto are related to the U-Boot DTB, while other modules are related to the kernel DTB. In the U-Boot phase, these two types of modules may need to be accessed crosswise at different times, and the modules themselves may need to access their own DTB node information.

These two types of modules belong to different DTBs, but `gd->fdt_blob` can only point to one of them and is not convenient to switch arbitrarily. How to solve this? Because the kernel dts will eventually be passed to the kernel for use, we cannot simply overlay certain nodes from the U-Boot dts onto the kernel dts to merge them into one.

Live dt can solve this problem. The principle of live dt is: during the initialization phase, U-Boot directly scans the entire DTB, converts all DTB nodes into a `struct device_node` linked list, and binds them to specific device-drivers. Thereafter, when a device-driver needs to access a DTB node, it directly accesses its own `device_node` without needing to access the original DTB.

Therefore, both the U-Boot and kernel DTBs are bound to their respective device-driver groups, and no longer need to directly access DTB files.

This solves the conflict caused by accessing two DTBs.

More references:

```
./doc/driver-model/livetree.txt
```

**fdt and live dt conversion:**

The `ofnode` type (include/dm/ofnode.h) is an encapsulation format that supports both types of dt. When using live dt, `device_node` is used to access dt nodes; when using fdt, offset is used to access dt nodes. When both types of drivers need to be supported simultaneously, use the `ofnode` type.

ofnode structure:

```c
 /*
  * @np: Pointer to device node, used for live tree
  * @of_offset: Pointer into flat device tree, used for flat tree. Note that this
  *      is not a really a pointer to a node: it is an offset value. See above.
  */
 typedef union ofnode_union {
         const struct device_node *np;   /* will be used for future live tree */
         long of_offset;
 } ofnode;
```

- Functions starting with "dev\_" and "ofnode\_" support both dt access methods;
- Functions starting with "of\_" are interfaces that only support live dt;
- Functions starting with "fdtdec\_" and "fdt\_" are interfaces that only support fdt;

### Mechanism Implementation

The kernel dtb switch is implemented in `init_kernel_dtb()` in `./arch/arm/mach-rockchip/board.c`. At this point, the U-Boot dts has already been scanned, and storage drivers such as mmc/nand/nor can work normally.

The kernel dtb is then read from the firmware, live dt table is built and all device-drivers are bound, and finally the `gd->fdt_blob` pointer is updated to point to the kernel dtb.

### U-Boot

- After U-Boot compilation is complete, two dtbs are generated in the `./dts/` directory:
  - dt.dtb: Compiled from the dts specified by `CONFIG_DEFAULT_DEVICE_TREE` in defconfig;
  - dt-spl.dtb: Obtained by extracting all nodes with the `u-boot,dm-pre-reloc` property from dt.dtb, then removing the properties specified by `CONFIG_OF_SPL_REMOVE_PROPS` in defconfig. It generally only contains nodes that drivers such as serial port, DDR, and storage must depend on: DMC, UART, MMC, NAND, GRF, CRU, etc.
- When `CONFIG_USING_KERNEL_DTB` is not enabled, the system uses dt.dtb; when `CONFIG_USING_KERNEL_DTB` is enabled, the system uses dt-spl.dtb.
- dt.dtb or dt-spl.dtb is renamed to u-boot.dtb after U-Boot compilation and then appended to the end of u-boot.bin. Users can check the content of u-boot.dtb using the fdtdump command.

## Kernel Parameter Passing

This chapter describes how U-Boot passes parameters to the kernel.

### cmdline

U-Boot reads `/chosen/bootargs` from the kernel DTB, modifies/appends new content, and then writes it back to the `/chosen/bootargs` node, thereby passing the cmdline.

## AB System

### AB Data Format

The A/B data structure is located at offset 2KB in the misc partition.

```c
/* Magic for the A/B struct when serialized. */
#define AVB_AB_MAGIC "\0AB0"
#define AVB_AB_MAGIC_LEN 4

/* Versioning for the on-disk A/B metadata - keep in sync with avbtool. */
#define AVB_AB_MAJOR_VERSION 1
#define AVB_AB_MINOR_VERSION 0

/* Size of AvbABData struct. */
#define AVB_AB_DATA_SIZE 32

/* Maximum values for slot data */
#define AVB_AB_MAX_PRIORITY 15
#define AVB_AB_MAX_TRIES_REMAINING 7

typedef struct AvbABSlotData {
  /* Slot priority. Valid values range from 0 to AVB_AB_MAX_PRIORITY,
   * both inclusive with 1 being the lowest and AVB_AB_MAX_PRIORITY
   * being the highest. The special value 0 is used to indicate the
   * slot is unbootable.
   */
  uint8_t priority;

  /* Number of times left attempting to boot this slot ranging from 0
   * to AVB_AB_MAX_TRIES_REMAINING.
   */
  uint8_t tries_remaining;

  /* Non-zero if this slot has booted successfully, 0 otherwise. */
  uint8_t successful_boot;

  /* Reserved for future use. */
  uint8_t reserved[1];
} AVB_ATTR_PACKED AvbABSlotData;

/* Struct used for recording A/B metadata.
 *
 * When serialized, data is stored in network byte-order.
 */
typedef struct AvbABData {
  /* Magic number used for identification - see AVB_AB_MAGIC. */
  uint8_t magic[AVB_AB_MAGIC_LEN];

  /* Version of on-disk struct - see AVB_AB_{MAJOR,MINOR}_VERSION. */
  uint8_t version_major;
  uint8_t version_minor;

  /* Padding to ensure |slots| field start eight bytes in. */
  uint8_t reserved1[2];

  /* Per-slot metadata. */
  AvbABSlotData slots[2];

  /* Reserved for future use. */
  uint8_t reserved2[12];

  /* CRC32 of all 28 bytes preceding this field. */
  uint32_t crc32;
} AVB_ATTR_PACKED AvbABData;
```

For small-capacity storage with no misc partition but a vendor partition, it can be stored in vendor.

On this basis, `lastboot` is added to mark the last bootable firmware. It is mainly used in low battery situations or during factory production testing when the retry count is exhausted before the system calls the boot_ctrl service. Reference as follows:

```c
typedef struct AvbABData {
  /* Magic number used for identification - see AVB_AB_MAGIC. */
  uint8_t magic[AVB_AB_MAGIC_LEN];

  /* Version of on-disk struct - see AVB_AB_{MAJOR,MINOR}_VERSION. */
  uint8_t version_major;
  uint8_t version_minor;

  /* Padding to ensure |slots| field start eight bytes in. */
  uint8_t reserved1[2];

  /* Per-slot metadata. */
  AvbABSlotData slots[2];

  /* mark last boot slot */
  uint8_t last_boot;
  /* Reserved for future use. */
  uint8_t reserved2[11];

  /* CRC32 of all 28 bytes preceding this field. */
  uint32_t crc32;
} AVB_ATTR_PACKED AvbABData;
```

At the same time, the `is_update` flag is added to `AvbABSlotData` to indicate the update status of the system. The changes are as follows:

```c
typedef struct AvbABSlotData {
  /* Slot priority. Valid values range from 0 to AVB_AB_MAX_PRIORITY,
   * both inclusive with 1 being the lowest and AVB_AB_MAX_PRIORITY
   * being the highest. The special value 0 is used to indicate the
   * slot is unbootable.
   */
  uint8_t priority;

  /* Number of times left attempting to boot this slot ranging from 0
   * to AVB_AB_MAX_TRIES_REMAINING.
   */
  uint8_t tries_remaining;

  /* Non-zero if this slot has booted successfully, 0 otherwise. */
  uint8_t successful_boot;

  /* Mark update state, mark 1 if the slot is in update state, 0 otherwise. */
  uint8_t is_update : 1;
  /* Reserved for future use. */
  uint8_t reserved : 7;
} AVB_ATTR_PACKED AvbABSlotData;
```

Finally, a table explains the meaning of each parameter:

AvbABData:

| **Parameter**    | **Description**                                              |
| ---------------- | ------------------------------------------------------------ |
| priority         | Slot priority, 0 means unbootable, 15 is the highest priority |
| tries_remaining  | Number of boot attempts, set to 7                            |
| successful_boot  | Configured after successful system boot, 1: slot booted successfully, 0: slot did not boot successfully |
| is_update        | Marks the update status of the slot, 1: slot is being updated, 0: slot is not updated or update was successful |

AvbABSlotData:

| **Parameter**   | **Description**                                              |
| --------------- | ------------------------------------------------------------ |
| magic           | Structure header information: \0AB0                           |
| version_major   | Major version information                                    |
| version_minor   | Minor version information                                    |
| slots           | Slot boot information, see AvbABData                         |
| last_boot       | The slot that booted successfully last time, 0: slot A booted successfully last time, 1: slot B booted successfully last time |
| crc32           | Data checksum                                                |

### AB Boot Modes

Currently, the system bootctrl designs two control modes, and bootloader supports booting from both modes.

#### successful-boot

After normal system entry, boot_ctrl sets the current slot variables based on `androidboot.slot_suffix`:

```
successful_boot = 1;
priority = 15;
tries_remaining = 0;
is_update = 0;
last_boot = 0 or 1;     :refer to androidboot.slot_suffix
```

```
Upgrading slot settings:
successful_boot = 0;
priority = 14;
tries_remaining = 7;
is_update = 1;
lastboot = 0 or 1;     :refer to androidboot.slot_suffix

Current slot settings:
successful_boot = 1;
priority = 15;
tries_remaining = 0;
is_update = 0;
last_boot = 0 or 1;     :refer to androidboot.slot_suffix
```

After system upgrade is complete, boot_ctrl sets:

#### Mode Comparison

- successful_boot mode
  - Advantage: As long as the system boots normally, it will not roll back to the old firmware version, unless configured by system bootctrl
  - Disadvantage: After long-term operation, if some storage particles become abnormal, the system may keep rebooting
- reset retry mode
  - Advantage: Always maintains the retry mechanism, can handle storage exception issues
  - Disadvantage: May roll back to the old firmware version

### Verification Methods

#### successful-boot

1. Burn only slot A, the system boots from slot A. Set boot from slot B, the system boots from slot A. Test completed, clear misc partition
2. Burn slot A and slot B, boot the system, current system is slot A. Set system to boot from slot B, reboot the system, current system is slot B. Test completed, clear misc partition
3. Burn slot A and slot B, quickly reset the system 14 times, after the retry counter is exhausted, it can still boot from the system specified by last_boot, i.e., it can boot normally from slot A. Test completed, clear misc partition
4. Burn slot A and slot B, boot the system, current system is slot A. Set system to boot from slot B, reboot the system, current system is slot B. Set system to boot from slot A, reboot the system, current system is slot A. Test completed, clear misc partition

#### reset-retry

1. Burn only slot A, the system boots from slot A. Set boot from slot B, the system boots from slot A. Test completed, clear misc partition
2. Burn slot A and slot B, boot the system, current system is slot A. Set system to boot from slot B, reboot the system, current system is slot B. Test completed, clear misc partition
3. Burn slot A and slot B, quickly reset the system 14 times, after the retry counter is exhausted, it can still boot from the system specified by last_boot, i.e., it can boot normally from slot A. Test completed, clear misc partition
4. Burn slot A and slot B, where slot B's boot.img is corrupted, boot the system, current system is slot A. Set system to boot from slot B, reboot the system, the system will restart 7 times and then boot normally from slot A. Test completed, clear misc partition
5. Burn slot A and slot B, boot the system, current system is slot A. Set system to boot from slot B, reboot the system, current system is slot B. Set system to boot from slot A, reboot the system, current system is slot A. Test completed, clear misc partition

### Terminology

AVB : Android Verified Boot

OTP & efuse : One Time Programmable

Product RootKey (PRK): The root key of AVB, verified by the root key that signs loader, uboot & trust

ProductIntermediate Key (PIK): Intermediate key, serves as an intermediary

ProductSigning Key (PSK): Key used for signing firmware

ProductUnlock Key (PUK): Key used for unlocking the device

**Keys are separated with clear responsibilities, which can reduce the risk of key leakage.**

### Introduction

This document introduces the Rockchip secure verified boot process. The so-called secure verified boot process is divided into security verification and integrity verification. Security verification is the verification of the public key. The process is: read the public key hash from secure storage (OTP & efuse), compare it with the calculated public key hash to check consistency, then use the public key to decrypt the firmware hash. Integrity verification is the verification of firmware integrity. The process is: load the firmware from storage, calculate the firmware hash and compare it with the decrypted hash for consistency.

### Encryption Example

The device's secure verified boot process is similar to the data encryption verification process in communication. This example can help accelerate understanding of the avb verification process. Suppose Alice wants to send digital information to Bob. To ensure the confidentiality, authenticity, integrity, and non-repudiation of the information transmission, the information needs to be digitally encrypted and signed. The transmission process is:

1. Alice prepares the digital information (plaintext) to be transmitted;

2. Alice performs a hash operation on the digital information to obtain a message digest;

3. Alice encrypts the message digest with her own private key to obtain Alice's digital signature, and appends it to the digital information;

4. Alice randomly generates an encryption key and uses this key to encrypt the information to be sent, forming ciphertext;

5. Alice encrypts the randomly generated encryption key with Bob's public key, and sends the encrypted DES key together with the ciphertext to Bob;

6. Bob receives the ciphertext and the encrypted DES key from Alice, first decrypts the encrypted DES key with his own private key, obtaining the encryption key randomly generated by Alice;

7. Bob then uses the random key to decrypt the received ciphertext, obtaining the plaintext digital information, and then discards the random key;

8. Bob decrypts Alice's digital signature with Alice's public key, obtaining the message digest;

9. Bob performs another hash operation on the received plaintext using the same hash algorithm, obtaining a new message digest;

10. Bob compares the received message digest with the newly generated message digest. If they match, it indicates that the received information has not been modified.

The DES algorithm mentioned above can be replaced with other algorithms, such as the AES encryption algorithm, and the public-private key algorithm can use the RSA algorithm. The flow is as follows:

### AVB

AVB stands for Android Verified Boot, a firmware verification process designed by Google, mainly used for verifying firmware such as boot and system. Rockchip Secure Boot references the verification methods in communication and AVB to implement a complete Secure Boot verification scheme.

#### AVB Features

- Security verification
- Integrity verification
- Anti-rollback protection
- persistent partition support
- chained partitions support, can use the same private key as boot and system, or the oem can keep the private key themselves, but must be signed by PRK

#### Key + Signature + Certificate

```shell
#!/bin/sh
touch temp.bin
openssl genpkey -algorithm RSA -pkeyopt rsa_keygen_bits:4096 -outform PEM -out testkey_prk.pem
openssl genpkey -algorithm RSA -pkeyopt rsa_keygen_bits:4096 -outform PEM -out testkey_psk.pem
openssl genpkey -algorithm RSA -pkeyopt rsa_keygen_bits:4096 -outform PEM -out testkey_pik.pem
python avbtool make_atx_certificate --output=pik_certificate.bin --subject=temp.bin --subject_key=testkey_pik.pem --subject_is_intermediate_authority --subject_key_version 42 --authority_key=testkey_prk.pem
python avbtool make_atx_certificate --output=psk_certificate.bin --subject=product_id.bin --subject_key=testkey_psk.pem --subject_key_version 42 --authority_key=testkey_pik.pem
python avbtool make_atx_metadata --output=metadata.bin --intermediate_key_certificate=pik_certificate.bin --product_key_certificate=psk_certificate.bin
```

permanent_attributes.bin generation:

```shell
python avbtool make_atx_permanent_attributes --output=permanent_attributes.bin --product_id=product_id.bin --root_authority_key=testkey_prk.pem
```

Among them, `product_id.bin` needs to be defined by the user, occupies 16 bytes, and can be defined as the product ID.

boot.img signing example:

```shell
avbtool add_hash_footer --image boot.img --partition_size 33554432 --partition_name boot --key testkey_psk.pem --algorithm SHA256_RSA4096
```

**Note: partition size must be at least 64K larger than the original firmware, and also 4K aligned, and must not exceed the partition size defined in parameter.txt.**

system.img signing example:

```shell
avbtool add_hashtree_footer --partition_size 536870912 --partition_name system --image system.img --algorithm SHA256_RSA4096 --key testkey_psk.pem
```

Generate vbmeta containing metadata.bin, example command:

```shell
python avbtool make_vbmeta_image --public_key_metadata metadata.bin --include_descriptors_from_image boot.img --include_descriptors_from_image system.img --generate_dm_verity_cmdline_from_hashtree system.img --algorithm SHA256_RSA4096 --key testkey_psk.pem  --output vbmeta.img
```

Finally, burn the generated vbmeta.img to the corresponding partition, e.g., the vbmeta partition.

#### AVB unlock

Currently, Rockchip uses strict security verification. The following needs to be added in the corresponding defconfig:

```
CONFIG_RK_AVB_LIBAVB_ENABLE_ATH_UNLOCK=y
```

Otherwise, entering `fastboot oem at-unlock-vboot` will unlock the device, and the device will boot successfully even if verification of vbmeta.img or boot.img fails.

First, generate PUK:

```shell
openssl genpkey -algorithm RSA -pkeyopt rsa_keygen_bits:4096 -outform PEM -out testkey_puk.pem
```

unlock_credential.bin is the certificate that needs to be downloaded to the device for unlocking. The generation process is as follows:

```shell
python avbtool make_atx_certificate --output=puk_certificate.bin --subject=product_id.bin --subject_key=testkey_puk.pem --usage=com.google.android.things.vboot.unlock --subject_key_version 42 --authority_key=testkey_pik.pem
```

To obtain unlock_credential.bin from the device, use the avb-challenge-verify.py script. Execute the following command to obtain unlock_credential.bin:

```shell
python avbtool make_atx_unlock_credential --output=unlock_credential.bin --intermediate_key_certificate=pik_certificate.bin --unlock_key_certificate=puk_certificate.bin --challenge=unlock_challenge.bin --unlock_key=testkey_puk.pem
```

Finally, the certificate can be downloaded to the device via fastboot command and unlock the device. The fastboot command is as follows:

```
fastboot stage unlock_credential.bin
fastboot oem at-unlock-vboot
```

The final operation flow is as follows:

1. The device enters fastboot mode. On the PC side, enter

```
fastboot oem at-get-vboot-unlock-challenge
fastboot get_staged raw_unlock_challenge.bin
```

Obtain data containing the version, Product Id, and a 16-byte random number. Extract the random number as unlock_challenge.bin.

2. Use avbtool to generate unlock_credential.bin, refer to make_unlock.sh.
3. On the PC side, enter

```
fastboot stage unlock_credential.bin
fastboot oem at-unlock-vboot
```

**Note**: At this point, the device must remain in the first fastboot mode state. During this time, it must not be powered off, shut down, or restarted. Because after step 1 is completed, the device stores the generated random number. If power is lost, the device is shut down, or restarted, the random number will be lost, and subsequent challenge signature verification will fail due to the random number mismatch.

If enabled:

```
CONFIG_MISC=y
CONFIG_ROCKCHIP_EFUSE=y
CONFIG_ROCKCHIP_OTP=y
```

Then CPUID will be used as the challenge number. Since CPUID is matched to the machine and data will not be lost due to shutdown, the generated unlock_credential.bin can be reused. This eliminates the need to repeatedly generate unlock_challenge.bin and create unlock_credential.bin. The unlock steps become:

```
fastboot oem at-get-vboot-unlock-challenge
fastboot stage unlock_credential.bin
fastboot oem at-unlock-vboot
```

avb-challenge-verify.py source code

```python
#/user/bin/env python
"This is a test module for getting unlock_challenge.bin"
import sys
import  os
from hashlib import sha256

def challenge_verify():
	if (len(sys.argv) != 3) :
		print "Usage: rkpublickey.py [challenge_file] [product_id_file]"
		return
	if ((sys.argv[1] == "-h") or (sys.argv[1] == "--h")):
		print "Usage: rkpublickey.py [challenge_file] [product_id_file]"
		return
	try:
		challenge_file = open(sys.argv[1], 'rb')
		product_id_file = open(sys.argv[2], 'rb')
		challenge_random_file = open('unlock_challenge.bin', 'wb')
		challenge_data = challenge_file.read(52)
		product_id_data = product_id_file.read(16)
		product_id_hash = sha256(product_id_data).digest()
		print("The challege version is %d" %ord(challenge_data[0]))
		if (product_id_hash != challenge_data[4:36]) :
			print("Product id verify error!")
			return
		challenge_random_file.write(challenge_data[36:52])
		print("Success!")

	finally:
		if challenge_file:
			challenge_file.close()
		if product_id_file:
			product_id_file.close()
		if challenge_random_file:
			challenge_random_file.close()

if __name__ == '__main__':
	challenge_verify()
```

## SD Boot and Upgrade

### Introduction

Rockchip divides SD cards into regular SD cards, SD upgrade cards, SD boot cards, and SD repair cards. The Rockchip creation of upgrade disk tool can be used to download update.img to the SD card to create different card types.

| **Card Type**   | **Function**                                                 |
| --------------- | ------------------------------------------------------------ |
| Regular SD card | Ordinary storage device                                      |
| SD upgrade card | The device boots from SD card to recovery, and recovery is responsible for updating the firmware from SD to device storage |
| SD boot card    | The device boots directly from the SD card                   |
| SD repair card  | Starting from pre-loader, copy firmware from SD card to device storage |

### Classification

#### Regular Card

Regular SD cards are used exactly the same as on a PC. They can be used as ordinary storage space in the U-Boot and Kernel systems. No tool operations are needed on the SD card.

#### Upgrade Card

The SD upgrade card is created using RK's tool to upgrade the firmware on local storage (e.g., eMMC, NAND flash) via SD card. SD card upgrade is a firmware upgrade method that can be done without a PC or network. Specifically, the SD card boot code is written to the reserved area of the SD card, and the firmware is copied to the visible partition of the SD card. When the main controller boots from the SD card, the SD card boot code and upgrade code burn the firmware into the local main storage. At the same time, the SD upgrade card supports PCBA testing and demo file copying. These features of the SD upgrade card allow firmware upgrades to be performed without a PC, improving production efficiency.

For an already prepared upgrade SD card, if only the firmware and demo files need to be updated, the following steps can be followed:

1. Copy the firmware to the SD card root directory and rename it to sdupdate.img
2. Copy demo files to the Demo directory under the SD card root directory

#### Boot Card

The SD boot card is created using RK's tool to enable direct booting from the SD card, greatly facilitating users to update and boot new firmware without re-burning firmware into device storage. The specific implementation is to burn the firmware into the SD card and use the SD card as the main storage. When the main controller boots from the SD card, the firmware and temporary files are all stored on the SD card. It can work normally whether or not there is local main storage. It is currently mainly used for device systems booting from SD card or for PCBA testing. **Note**: PCBA testing is just a functional item under recovery and can be used for both upgrade cards and boot cards.

#### Repair Card

The SD repair card is similar to the SD card upgrade function, but the firmware upgrade is done by miniloader. First, the tool writes the boot code to the reserved area of the SD card, then copies the firmware to the visible partition of the SD card. When the main controller boots from the SD card, the SD card upgrade code upgrades the firmware to the local main storage. It is mainly used for repairing devices with damaged firmware.

### Firmware Flags

SD cards serving different functions have certain flags set in the SD card.

At sector 64 of the SD card, if the start flag (magic number) is 0xFCDC8C3B, it is a special card. Firmware will be read from the SD card to boot the device. If not, it is treated as a regular SD card. At offset (sector 64 + 616 bytes), the flags for various card types are stored. Currently, there are three types:

| **Flag** | **Card Type**               |
| -------- | --------------------------- |
| 0        | Upgrade card or PCBA test card |
| 1        | Boot card                   |
| 2        | Repair card                 |

### Boot Flow

The SD card boot flow can be divided into the pre-loader boot flow and the uboot boot flow. Both flows need to load and detect the SD card and the Startup Flag in the IDB Block of the SD card, and execute different functions based on these flags. The flow is as follows:

![sd-system-bringup-frame](./Rockchip_Developer_Guide_UBoot_Nextdev/SD_Boot/sd-system-bringup-frame.jpg)

#### pre-loader Boot

![loader-flow](./Rockchip_Developer_Guide_UBoot_Nextdev/SD_Boot/loader-flow.jpg)

maskrom first finds an available miniloader firmware (the boot storage media and priority order supported by maskrom can be determined from the TRM; maskrom sequentially scans firmware on available storage), then jumps to miniloader. miniloader re-scans storage devices. If an SD card is detected, it checks whether the SD card contains IDB format firmware. If so, it then determines the card flag. If the SD card is available and the flag is '0' or '1', it reads the U-Boot firmware from the SD card, loads and starts U-Boot. If the flag is '2', it enters the repair card flow and updates firmware under the loader. The normal boot flow is to scan other storage and load the next-level loader.

Upgrade card: U-Boot re-scans storage devices. If an SD card is detected, it checks whether the SD card contains IDB format firmware. If so, it checks whether the card flag is 0 and adds 'sdfwupdate' to the cmdline passed to the kernel. Finally, it reads the misc partition of the SD card to get the card boot mode. If it is recovery mode, it loads and starts recovery.
Boot card: U-Boot re-scans storage devices. If an SD card is detected, it checks whether the SD card contains IDB format firmware. If so, it checks whether the card flag is 1. Finally, it reads the misc partition of the SD card to get the card boot mode. If it is recovery, it loads and starts recovery. If it is normal mode, it loads and starts the kernel.

### Notes

- When creating non-GPT format firmware, U-Boot needs to configure CONFIG_RKPARM_PARTITION.
- When creating an SD upgrade card, update.img must include MiniloaderAll.bin, parameter.txt, uboot.img, trust.img, misc.img, resource.img, and recovery.img. Otherwise, burning update.img will prompt a "Write MBR failed" error.
