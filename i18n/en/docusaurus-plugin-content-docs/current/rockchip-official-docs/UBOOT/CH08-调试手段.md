# Debugging Methods

This chapter mainly introduces some commonly used debugging methods in the U-Boot phase, including the use of commands, scripts, configuration options, boot messages, etc.

## DEBUG

Function: Enable global `debug()` printing.

You can add a macro definition in rkxxx_common.h for each platform to enable it:

```
#define DEBUG
```

## io Command

Function: Read/write memory.

```c
// Read operation
md - memory display
Usage: md [.b, .w, .l, .q] address [# of objects]

// Write operation
mw - memory write (fill)
Usage: mw [.b, .w, .l, .q] address value [count]
```

Read operation. Example: Display 0x10 consecutive data starting from address 0x76000000.

```c
=> md.l 0x76000000 0x10
76000000: fffffffe ffffffff ffffffff ffffffff    ................
76000010: ffffffdf ffffffff feffffff ffffffff    ................
76000020: ffffffff ffffffff ffffffff ffffffff    ................
76000030: ffffffff ffffffff ffffffff ffffffff    ................
```

Write operation. Example: Assign value 0x1234 to address 0x76000000.

```c
=> mw.l 0x76000000 0xffff1234 // High 16 bits have mask
=> md.l 0x76000000 0x10       // Read back
76000000: ffff1234 ffffffff ffffffff ffffffff    ................
76000010: ffffffdf ffffffff feffffff ffffffff    ................
76000020: ffffffff ffffffff ffffffff ffffffff    ................
76000030: ffffffff ffffffff ffffffff ffffffff    ................
```

## iomem Command

Function: Read memory. More flexible than the md command, it automatically resolves DTS node to get the base address.

```c
=> iomem
iomem - Show iomem data by device compatible

Usage:
// @<compatible>: Keyword matching of the node's compatible part
iomem <compatible> <start offset>  <end offset>
eg: iomem -grf 0x0 0x200
```

Example: RK3228 read GRF data from 0x00 to 0x20:

```c
// Here, "-grf" is used as the keyword to distinguish it from "rockchip, rk3288-pmugrf"
=> iomem -grf 0x0 0x20
rockchip,rk3228-grf:
11000000:  00000000 00000000 00004000 00002000
11000010:  00000000 00005028 0000a5a5 0000aaaa
11000020:  00009955
```

## i2c Command

Function: Read/write i2c devices.

```
=> i2c
i2c - I2C sub-system

Usage:
i2c dev [dev] - show or set current I2C bus
i2c md chip address[.0, .1, .2] [# of objects] - read from I2C device
i2c mw chip address[.0, .1, .2] value [count] - write to I2C device (fill)
......
```

Read operation. Example:

```c
=> i2c dev 0                     // Switch to i2c0 (specify once)
Setting bus to 0

=> i2c md 0x1b 0x2e 0x20         // i2c device address is 0x1b (7-bit address), read 0x20 consecutive register values starting from 0x2e
002e: 11 0f 00 00 11 0f 00 00 01 00 00 00 09 00 00 0c    ................
003e: 00 0a 0a 0c 0c 0c 00 07 07 0a 00 0c 0c 00 00 00    ................
```

Write operation. Example:

```c
=> i2c dev 0                     // Switch to i2c0 (specify once)
Setting bus to 0

=> i2c mw 0x1b 0x2e 0x10         // i2c device address is 0x1b (7-bit address), assign 0x10 to register 0x2e
=> i2c md 0x1b 0x2e 0x20         // Read back
002e: 10 0f 00 00 11 0f 00 00 01 00 00 00 09 00 00 0c    ................
003e: 00 0a 0a 0c 0c 0c 00 07 07 0a 00 0c 0c 00 00 00    ................
```

```

```

## fdt Command

Function: Print DTB content.

```
=> fdt
fdt - flattened device tree utility commands

Usage:
fdt addr [-c]  <addr> [<length>]    - Set the [control] fdt location to <addr>
fdt print  <path> [<prop>]          - Recursive print starting at <path>
fdt list   <path> [<prop>]          - Print one level starting at <path>
......
NOTE: Dereference aliases by omitting the leading '/', e.g. fdt print ethernet0.
```

The following two combined commands can dump the complete device-tree:

```c
=> fdt addr $fdt_addr_r   // Specify fdt address
=> fdt print              // Print all fdt content
```

## mmc Command

Function: MMC device read/write, switching.

MMC device info:

```c
=> mmc info
Device: dwmmc@ff0f0000                  // Device node
Manufacturer ID: 15
OEM: 100
Name: 8GME4
Timing Interface: High Speed            // Speed mode
Tran Speed: 52000000                    // Current speed
Rd Block Len: 512
MMC version 5.1
High Capacity: Yes
Capacity: 7.3 GiB                       // Storage capacity
Bus Width: 8-bit                        // Bus width
Erase Group Size: 512 KiB
HC WP Group Size: 8 MiB
User Capacity: 7.3 GiB WRREL
Boot Capacity: 4 MiB ENH
RPMB Capacity: 512 KiB ENH
```

MMC device switching:

```c
=> mmc dev 0                            // Switch to eMMC
=> mmc dev 1                            // Switch to SD card
```

MMC device read/write:

```c
mmc read addr blk# cnt
mmc write addr blk# cnt
mmc erase blk# cnt
Example:
=> mmc read 0x70000000 0 1    // Read the first block of the MMC device, 1 sector of data to memory at 0x70000000
=> mmc write 0x70000000 0 1   // Write 1 sector of data from memory at 0x70000000 to the first block of the storage
=> mmc erase 0 1              // Erase 1 sector starting from the first block of the storage
```

If the MMC device read/write is abnormal, you can quickly locate the issue through the following simple steps:

Change `debug()` to `printf()` in drivers/mmc/dw_mmc.c, then recompile and flash. Check the MMC device's print information:

- If the last print is Sending CMD0, please check the hardware power supply and pin connections; check if the software IOMUX has been taken by another IP.
- If the last print is Sending CMD8, configure the MMC device to allow access to secure storage in the security software part.
- If all initialization commands have passed and the last print is Sending CMD18, please check the MMC hardware power supply, whether the capacitors near the MMC power supply terminal are sufficient (try replacing with larger capacitors), and in software, reduce the clock frequency or switch the MMC device's speed mode.

```

----------------------------------------------------------

 serial     [ + ]   ns16550_serial             |-- serial@11030000 *
 clk        [ + ]   clk_rk322x                 |-- clock-controller@110e0000
```

Print meaning:

## HASH Verification

Function: Verify the integrity of Android format firmware.

```
ANDROID_BOOT_IMAGE_HASH
```

After enabling this configuration, the integrity of the firmware will be verified when loading Android format firmware.

Due to historical reasons, if the above configuration cannot correctly verify the firmware, please also enable the following configuration:

```
HASH_ROCKCHIP_LEGACY
```

## Modifying DDR Capacity

At boot, the DDR initialization code passes the DDR capacity to U-Boot. U-Boot removes some secure memory and then passes it to the kernel. Users can modify the DDR capacity passed to the kernel during the U-Boot phase.

Passing example:

```c
......
// Available memory blocks passed to the kernel (secure memory blocks have been removed).
Adding bank: 0x00200000 - 0x08400000 (size: 0x08200000)
Adding bank: 0x0a200000 - 0x40000000 (size: 0x35e00000)
Total: 895.411 ms

Starting kernel ...
[    0.000000] Booting Linux on physical CPU 0x0
```

Code location:

```c
./arch/arm/mach-rockchip/param.c
```

Modification location:

```c
struct memblock *param_parse_ddr_mem(int *out_count)
{
	......

	// This is the capacity information passed from ddr to U-Boot.
	// Since non-contiguous addresses may occur, it is passed in blocks,
	// indicating the start address and size of each memory block.
	// PS: Generally, it is contiguous memory, so no block splitting is needed.
	for (i = 0, n = 0; i < count; i++, n++) {
		// For example, 2GB capacity (contiguous address): count=1, base = 0, size = 0x80000000.
		// Users can modify as needed during debugging.
		base = t->u.ddr_mem.bank[i];
		size = t->u.ddr_mem.bank[i + count];

		/* 0~4GB */
		if (base < SZ_4GB) {
			mem[n].base = base;
			mem[n].size = ddr_mem_get_usable_size(base, size);
			if (base + size > SZ_4GB) {
				n++;
				mem[n].base_u64 = SZ_4GB;
				mem[n].size_u64 = base + size - SZ_4GB;
			}
		} else {
			/* 4GB+ */
			mem[n].base_u64 = base;
			mem[n].size_u64 = size;
		}

		assert(n < count + MEM_RESV_COUNT);
	}
	......
}
```

## Jump Information

Function: Confirm firmware version and flow. In some cases, boot information can also help users locate some crash issues.

1. System hangs after trust finishes

Possible reason: The firmware packaging or flashing is faulty, causing trust to jump to the wrong U-Boot start address. Users can confirm through the U-Boot start address printed by trust.

For 64-bit platforms, the U-Boot start address is typically offset 0x200000 (DRAM start address is 0x0):

```c
NOTICE:  BL31: v1.3(debug):d98d16e
NOTICE:  BL31: Built : 15:03:07, May 10 2018
NOTICE:  BL31: Rockchip release version: v1.1
INFO:    GICv3 with legacy support detected. ARM GICV3 driver initialized in EL3
INFO:    Using opteed sec cpu_context!
INFO:    boot cpu mask: 0
INFO:    plat_rockchip_pmu_init(1151): pd status 3e
INFO:    BL31: Initializing runtime services
INFO:    BL31: Initializing BL32
INFO:    BL31: Preparing for EL3 exit to normal world
INFO:    Entry point address = 0x200000	 // U-Boot address
INFO:    SPSR = 0x3c9
```

For 32-bit platforms, the U-Boot start address is typically offset 0x0 (DRAM start address is 0x60000000):

```c
INF [0x0] TEE-CORE:init_primary_helper:378: Release version: 1.9
INF [0x0] TEE-CORE:init_primary_helper:379: Next entry point address: 0x60000000  // U-Boot address
INF [0x0] TEE-CORE:init_teecore:83: teecore inits done
```

2. U-Boot version backtracking:

The compilation version can be backtracked through the U-Boot boot information. The following corresponds to commit: b34f08b.

```
U-Boot 2017.09-01730-gb34f08b (Jul 06 2018 - 17:47:52 +0800)
```

If "dirty" appears in the boot information, it means there were local modifications at compile time that were not committed to the repository, so the compile point is not clean.

```
U-Boot 2017.09-01730-gb34f08b-dirty (Jul 06 2018 - 17:35:04 +0800)
```

## Boot Information

Users can obtain the current U-Boot flow and the status of various peripherals through the U-Boot boot information, making it easy to quickly locate anomalies.

Currently, U-Boot supports three firmware type boot methods: Android format > RK format > DISTRO format. The RK SDK mainly uses the first two firmware formats, while DISTRO is generally used by open-source users.

Note: If the user's code is not new enough, some prints may not be visible, but this does not affect the user's overall understanding of the U-Boot boot information.
